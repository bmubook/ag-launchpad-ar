# 🛡️ بوابة الإجماع — `/consensus-gate`

تطبيق البند 7 (`rules_workflow.md`) بمراجعين **مستقلين فعلياً**: ثلاثة وكلاء فرعيين (Subagents) يبدأ كل منهم بسياق نظيف لا يرى المحادثة، فلا يتأثر بتبريرك للكود الذي كتبته.

* **النطاق الذي مرّره المستخدم:** $ARGUMENTS
* إذا كان النطاق فارغاً: راجِع التعديلات الحالية وفق الخطوة 1.

| الرمز | المراجع | الوكيل الفرعي | مجال الفحص |
|:---:|:---|:---|:---|
| 🔒 | مُراجع الأمن | `security-critic` | الأسرار و `.env`، قواعد الأمان، الحقن، الصلاحيات، الاعتماديات، الهجرات |
| ⚡ | مُراجع الأداء | `performance-critic` | سقوف الحجم، الكود النظيف، الأداء، الاستعلامات، الاختبارات |
| 🎨 | مُراجع تجربة المستخدم | `ux-critic` | tokens، حالات المكونات، التجاوب، الوصولية، RTL والتعريب |

## الخطوة 1 — تحديد مجموعة التعديلات (Change Set)

**شرط مسبق — الفحص الآلي أولاً:** شغّل `node .claude/scripts/verify.mjs --status`. إذا لم تكن بوابة الإثبات ناجحة فشغّل `node .claude/scripts/verify.mjs` وأصلح حتى تنجح قبل استدعاء أي مراجع؛ لا يُنفق رصيد المراجعين على كود لا ينجح فحصه الآلي. مشروع بلا أوامر فحص بعد ← اذكر ذلك في خانة الملاحظات وتابع.

نفّذ الأوامر بأداة Bash (كلها للقراءة فقط). حدّد الفرع الرئيسي أولاً: `main` إن وُجد (`git rev-parse --verify --quiet main`) وإلا `master`، ويُشار إليه أدناه بـ `<main>`. إذا مرّر المستخدم نطاقاً: هو فرع إذا نجح `git rev-parse --verify --quiet <النطاق>`، وإلا فهو مسارات ملفات أو مجلدات.

| الحالة | أوامر الحصر والعدّ | أمر الفحص الذي يُمرَّر للمراجعين |
|:---|:---|:---|
| نطاق ملفات أو مجلدات | `git diff --numstat HEAD -- <المسارات>` و `git ls-files --others --exclude-standard -- <المسارات>` | `git diff HEAD -- <المسارات>` |
| نطاق فرع | `git diff --stat <main>...<الفرع>` و `git diff --numstat <main>...<الفرع>` | `git diff <main>...<الفرع>` |
| بلا نطاق، وتوجد تعديلات غير مُلتزَمة (`git status --porcelain` غير فارغ) | `git diff --stat HEAD` و `git diff --numstat HEAD` و `git ls-files --others --exclude-standard` | `git diff HEAD -- <الملفات>` |
| بلا نطاق، وشجرة العمل نظيفة | `git diff --stat <main>...HEAD` و `git diff --numstat <main>...HEAD` | `git diff <main>...HEAD` |

**عدّ الأسطر المتغيرة:**
* المجموع = (المضافة + المحذوفة) لكل ملف من `--numstat` + عدد أسطر كل ملف جديد غير متتبَّع (`wc -l <الملف>`).
* تُستبعد من العدّ والمراجعة: سجلات الحالة الأربعة (`changelog.md`، `project_map.md`، `bugs_log.md`، `decisions_log.md`) والملفات الثنائية (تظهر بعلامة `-` في `--numstat`).
* ملفات القفل (`package-lock.json`، `pnpm-lock.yaml`، `yarn.lock`، `pubspec.lock`) لا تُعدّ أسطرها، لكن وجودها يجعل التعديل **كبيراً** (الخطوة 3).

**حالات خاصة:**

| الحالة | التصرف |
|:---|:---|
| لا توجد تعديلات | أبلغ المستخدم: `لا توجد تعديلات تحتاج مراجعة.` وتوقف |
| مستودع بلا أي Commit (`git rev-parse --verify HEAD` يفشل) | كل الملفات جديدة: احصرها بـ `git status --porcelain`، واطلب من المراجعين قراءتها كاملة |
| المشروع غير مهيأ لـ Git | نبّه برسالة البند 15، واعتمد الملفات التي أنشأتها أو عدّلتها في هذه الجلسة؛ يقرؤها المراجعون كاملة |

## الخطوة 2 — وضع التشغيل وطبيعة المشروع

اقرأ من `project_map.md` السطرين التاليين (القيمة التي تبدأ بـ `[` تعني "غير محددة"):

|:---|:---|

**وضع `prototype`:** البوابة معطلة (البند 1 — `master_rules.md`). نفّذ مراجعة أمنية ذاتية سريعة فقط واعرضها:

| الفحص الأمني السريع | المرجع | النتيجة |
|:---|:---:|:---:|
| لا مفاتيح أو كلمات مرور مكتوبة في الكود | البند 5 | ✅ / ❌ |
| المتغيرات الحساسة تُقرأ من `.env`، و `.env.example` يحوي الأسماء فقط | البند 5 | ✅ / ❌ |
| قواعد الأمان (`firestore.rules` و `storage.rules`) مغلقة افتراضياً وتحمي كل مجموعة جديدة أو معدّلة — لا «وضع اختبار» | البند 5 | ✅ / ❌ |
| لا محتوى مستورد يُعامَل كأوامر | البند 6 | ✅ / ❌ |

* أي ❌ يُصلَح قبل المتابعة؛ البندان 5 و 6 ساريان في كل الأوضاع.
* قيمة خانة الإجماع في `changelog.md`: `مراجعة ذاتية`. ثم توقف هنا.

## الخطوة 3 — تصنيف التعديل (البند 7)

طبّق الشروط **بالترتيب**؛ أول شرط يتحقق يحدد الفئة (عند التعارض تغلب الفئة الأعلى):

| الترتيب | الشرط | الفئة | المراجعون |
|:---:|:---|:---:|:---|
| 1 | يمس مجالاً أمنياً أو بنيوياً (الجدول التالي) مهما كان حجمه | 🔴 كبير | الثلاثة |
| 2 | أكثر من 50 سطراً | 🔴 كبير | الثلاثة |
| 3 | أقل من 20 سطراً، أو CSS بحت، أو إصلاح نصي، أو تعليقات توثيقية فقط | 🟢 صغير | مراجعة ذاتية فقط |
| 4 | من 20 إلى 50 سطراً | 🟡 متوسط | مراجع واحد حسب طبيعة التعديل |

**المجالات الأمنية والبنيوية (تجعل التعديل كبيراً تلقائياً):**

| المجال | أمثلة على المسارات والمحتوى |
|:---|:---|
| المصادقة والجلسات | `auth/`، تسجيل الدخول، الجلسات، التوكنز، كلمات المرور، OAuth، Middleware الحماية |
| قاعدة البيانات | `firestore.rules`، `storage.rules`، `firestore.indexes.json`، `firebase.json`، `scripts/migrations/` (وعند قاعدة علاقية: `migrations/`، `*.sql`) |
| الصلاحيات | قواعد الأمان، الأدوار (Custom Claims)، App Check |
| متغيرات البيئة | `.env.example`، قراءة متغير بيئة جديد |
| الاعتماديات | `package.json` (قسم dependencies)، ملفات القفل، `requirements.txt`، `pubspec.yaml` |
| الإعدادات | `*.config.*`، `tsconfig.json`، `Dockerfile`، `.github/workflows/`، `.claude/settings.json`، `.claude/hooks/` |
| نقاط الـ API | `api/`، `app/api/`، `pages/api/`، `routes/`، `server/`، `functions/` (Cloud Functions) |

**اختيار المراجع في التعديل المتوسط:**

| طبيعة التعديل الغالبة | المراجع |
|:---|:---|
| مدخلات المستخدم، رفع الملفات، استدعاء خدمات خارجية، بيانات شخصية | 🔒 `security-critic` |
| منطق برمجي، خوارزميات، استعلامات، إدارة الحالة، أداء | ⚡ `performance-critic` |
| ملفات واجهات: HTML/JSX/TSX/Vue/Svelte، CSS مع مكونات، واجهات Flutter أو React Native، `locales/` | 🎨 `ux-critic` |
| طبيعة مختلطة | الأعلى في ترتيب الأولويات (البند 0): 🔒 ثم ⚡ ثم 🎨 |

* **مشروع باك إند فقط:** لا يُستدعى `ux-critic` أبداً وينتقل وزنه إلى الأمن والأداء؛ في التعديل الكبير يشارك 🔒 و ⚡ فقط.
* **التعديل الصغير:** مراجعة ذاتية سريعة = بنود الفحص الأمني في الخطوة 2 + لا كود ناقص أو `TODO` (البند 11) + الملف ضمن سقفه (البند 14) + للواجهات: القيم من tokens والخصائص المنطقية (Logical Properties). اعرض سطراً واحداً، مثل:
  `🔍 مراجعة ذاتية (تعديل صغير — 12 سطراً): ✅ لا أسرار · ✅ لا كود ناقص · ✅ ضمن سقف الحجم`
  وقيمة خانة الإجماع: `مراجعة ذاتية`. ثم توقف.
* **قبل تشغيل المراجعين** أعلن التصنيف في سطر واحد، مثل:
  `🛡️ بوابة الإجماع: تعديل كبير (74 سطراً، يشمل هجرة قاعدة بيانات) ← 3 مراجعين بالتوازي`

## الخطوة 4 — تشغيل المراجعين بالتوازي

* أرسل **رسالة واحدة** تحتوي استدعاءً لأداة `Agent` لكل مراجع مختار، مع `subagent_type` = اسم المراجع (`security-critic` أو `performance-critic` أو `ux-critic`). لا تشغّلهم في الخلفية، ولا واحداً بعد الآخر.
* لا تعدّل أي ملف أثناء عمل المراجعين؛ يجب أن يراجعوا اللقطة نفسها من الكود.
* **الاستقلالية شرط:** مرّر الحقائق فقط. لا تذكر رأيك في جودة الكود، ولا الدرجة المتوقعة، ولا تبريرات التصميم.
* نص التكليف لكل مراجع (املأ كل الحقول):

```text
مراجعة بوابة الإجماع — الجولة <1 أو 2 أو 3> من 3
- طبيعة المشروع: <القيمة من project_map.md>
- وضع التشغيل: production
- فئة التعديل وسببها: <كبير أو متوسط> — <سبب التصنيف>
- هدف التعديل في سطر واحد: <ما يُفترض أن يفعله الكود>
- الملفات المتغيرة (+مضافة/-محذوفة):
  - <المسار> (+<عدد>/-<عدد>)
- أمر فحص الفروقات: <مثل: git diff HEAD -- src/auth/login.ts>
- ملفات جديدة غير متتبَّعة (اقرأها كاملة بأداة Read): <القائمة، أو: لا يوجد>
- ملاحظات الجولة السابقة وما عولج منها: <للجولتين 2 و 3 فقط، وإلا: لا يوجد>
أعد تقريرك بالصيغة المحددة في تعريفك حرفياً.
```

## الخطوة 7 — عند الفشل: الإصلاح الداخلي (3 جولات كحد أقصى)

الجولة = تشغيل واحد للمراجعين؛ الجولة 1 هي المراجعة الأولى، والحد الأقصى 3 جولات.

1. أصلح الكود داخلياً بناءً على ملاحظات المراجعين الراسبين، دون إغراق المستخدم بتفاصيل الفشل التقنية (البند 7):
   * حلّل السبب الجذري قبل الإصلاح (البند 22)، وعدّل جزئياً بأداة `Edit` (البند 14).
   * يُحظر إضعاف الأمان أو فتح قواعد الأمان أو تزييف البيانات لرفع الدرجة (البند 11) — هذا فشل كارثي.
   * شغّل الاختبارات الموجودة إن وُجدت (البند 16).
2. إذا مسّ الإصلاح مجالاً أمنياً أو بنيوياً (جدول الخطوة 3) ولم يكن 🔒 مشاركاً، أضِف `security-critic` إلى الجولة التالية.
3. أعد تشغيل **المراجعين الراسبين فقط** بالتوازي، مع رقم الجولة، وجدول ملاحظاتهم السابقة، وملخص ما تغيّر، وأمر الفحص المحدَّث.
4. اعرض جدول الجولة (الخطوة 6) وتابع.

**بعد فشل الجولة الثالثة:**

1. أوقف أي تعديل إضافي.
2. سجّل المشكلة في `bugs_log.md` بالقالب الكامل:
   * **صف في جدول `ملخص الأخطاء النشطة`:**
     `| <الرقم التالي> | <YYYY-MM-DD> | <🔴 أو 🟡 أو 🟢> | <الملف المتسبب> | فشل بوابة الإجماع بعد 3 جولات: <وصف مختصر> | ⏳ نشط — بانتظار قرار المستخدم |`
     إن كان الجدول يحوي صف "لا توجد" فاستبدله بهذا الصف. الأولوية: 🔴 إذا بقيت ملاحظة حرجة، 🟡 إذا بقيت عالية أو متوسطة، 🟢 لغير ذلك.
   * **قسم تفصيلي** بعد القالب تحت `تفاصيل الأخطاء الكاملة` (دون حذف القالب)، بعنوان `### خطأ #<الرقم> — فشل بوابة الإجماع (<التاريخ>)`، يملأ حقول القالب التسعة بالترتيب:

     | الحقل | المحتوى |
     |:---|:---|
     | الخطأ المكتشف ورسالته | درجات الجولة الثالثة وأهم الملاحظات غير المحلولة |
     | الملف المتسبب وسطر الكود | `path:line` لكل ملاحظة متبقية |
     | خطوات إعادة الإنتاج | تشغيل `/consensus-gate` على النطاق نفسه ← المتوقع ≥ 8 من كل مراجع مقابل الدرجات الفعلية |
     | الجذر التقني | نتيجة تحليل السبب الجذري (البند 22) |
     | الميزات المتأثرة | الميزات أو الوحدات التي يمسها التعديل |
     | طريقة الإصلاح | ما جُرّب في الجولتين 2 و 3 ولماذا لم يكفِ |
     | رقم المحاولة | `3/3` |
     | مرجع Git | ناتج `git rev-parse --abbrev-ref HEAD` و `git rev-parse --short HEAD` |
     | حالة الأمان وقواعد الحماية | من آخر تقرير لـ `security-critic`، أو "لم يشارك مُراجع الأمن" |

3. أبلغ المستخدم في سطرين بلغة بسيطة بما تعذّر ولماذا، ثم اسأله بأداة `AskUserQuestion` (سؤال واحد) عن الخطوة التالية:

   | الخيار | الوصف |
   |:---|:---|
   | ترجيع التعديلات | العودة لآخر حالة مستقرة وفق البند 15 (الأوامر المدمّرة تحتاج موافقته في نافذة الصلاحيات) |
   | تبسيط المهمة | تقسيم الميزة أو تقليص نطاقها، ثم إعادة البوابة من الجولة 1 |
   | عرض التفاصيل | شرح الملاحظات التقنية كاملة ليوجّه طريقة الإصلاح |
   | استثناء موثّق | فقط إذا لم يكن مُراجع الأمن بين الراسبين: قبول مؤقت يُوثَّق في `decisions_log.md` ويبقى الخطأ نشطاً |

   * لا يُعرض خيار الاستثناء إذا رسب مُراجع الأمن؛ الأمن أولاً (البند 0).
4. اختم الرد بـ: `📋 التوثيق: ⬜ changelog (لم يعبر التعديل البوابة) | ⬜ project_map (لا تغيير) | ✅ bugs_log | ⬜ decisions_log (لا قرارات جديدة)`. إذا ذكّرك Hook التوقف بتحديث `changelog.md`، فوضّح أن التعديل لم يعبر البوابة وأن المشكلة مسجلة في `bugs_log.md`.

## الخطوة 8 — عند العبور: تسجيل الدرجات

1. **الفحص التشغيلي أولاً (البند 8):** شغّل كل الاختبارات الموجودة (البند 16) على فرع العمل المؤقت عبر أداة Bash. فشلها يخضع لحد المحاولات الثلاث في البند 8.
2. **سجّل الدرجات** في الخانة الأخيرة `نتيجة درجات الإجماع (Consensus Score)` من جدول `changelog.md`:

| الحالة | القيمة |
|:---|:---|
| ثلاثة مراجعين | `🔒 9 · ⚡ 8 · 🎨 9` |
| مشروع باك إند فقط | `🔒 9 · ⚡ 8.5` |
| مراجع واحد (تعديل متوسط) | `⚡ 9` |
| تعديل صغير أو وضع `prototype` | `مراجعة ذاتية` |

* الترتيب ثابت: 🔒 ثم ⚡ ثم 🎨، والفاصل ` · `، ويُحذف المراجع غير المشارك.
* الدرجة المسجلة لكل مراجع = درجته في آخر جولة شارك فيها.
* **طريقة التسجيل:**
  * إذا تغيّر كود (تعديل جديد لم يُوثَّق بعد، أو إصلاحات أثناء الجولات): نفّذ `/document` بأداة Skill ومرّر له قيمة الخانة ليكتبها في صف التعديل مع ختم التوثيق.
  * إذا كان صف التعديل موجوداً في `changelog.md` ولم يتغير أي كود أثناء البوابة: عدّل الخانة الأخيرة في ذلك الصف فقط بأداة `Edit`.
