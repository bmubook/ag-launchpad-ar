# /launch-check — هل تطبيقك جاهز للإطلاق؟

> **المبدأ:** الأمان أولاً (البند 0 — `master_rules.md`). أي بند ❌ في مجموعة الأمان يعني 🔴 غير جاهز مهما كانت بقية النتائج. هذه المهارة تفحص وتقرّر؛ الإصلاحات تُنفَّذ بعد موافقة المستخدم كمهام مستقلة.

## 1. التحضير
1. اقرأ `project_map.md` (الطبيعة، الـ Stack، الوضع) و`bugs_log.md` (الأخطاء النشطة) و`.env.example`.
2. طبّق فقط المجموعات المناسبة لطبيعة المشروع (SEO للويب، المتاجر للجوال).

## 2. الفحوص الآلية (شغّلها فعلياً وسجّل النتيجة)
| الفحص | الأمر |
|:---|:---|
| الاختبارات والتدقيق والبناء | أوامر `check` أو `lint` و `test` و `build` من `/quality-setup` (أو `flutter analyze` و `flutter test`) |
| أحجام الملفات | `node .claude/scripts/size-report.mjs` |
| ثغرات الاعتماديات | `npm audit --omit=dev` (أو ما يعادله لمدير الحزم) / `flutter pub outdated` |
| أسرار متتبَّعة في Git | `git ls-files` بلا أي ملف `.env` حقيقي ولا ملف حساب خدمة (`*adminsdk*.json`)، ثم `git grep -n -I -e sk_live_ -e "PRIVATE KEY" -e service_account` على الفرع الحالي |
| قواعد الأمان | افحص `firestore.rules` و `storage.rules`: لا `if true` ولا شرط تاريخ «وضع الاختبار»، والقاعدة الختامية `match /{document=**}` مغلقة، ولكل مجموعة يستخدمها الكود قاعدة؛ ثم شغّل `firebase emulators:exec "npm run test:rules"` |

## 3. قائمة الفحص (✅ / ⚠️ / ❌ لكل بند مع طريقة التحقق)
**🛡️ الأمان:** قواعد الأمان مغلقة افتراضياً وبأقل صلاحية لكل مجموعة ومسار تخزين (البند 5) · App Check مفعّل · لا أسرار في الكود أو Git · `.env.example` يغطي كل المتغيرات بقيم فارغة · التحقق من الصلاحيات في كل نقطة API · التحقق من المدخلات (Zod أو ما يعادله) · التوكنز في httpOnly cookies للويب (البند 28) · حد للطلبات (Rate Limiting) على تسجيل الدخول والنماذج · HTTPS في الاستضافة · متغيرات البيئة مضبوطة في الاستضافة لا في الكود.
**⚡ الأداء (البند 26):** حجم الحزمة ≤ 250KB لكل جزء، والتحميل الكسول للصور والمكونات، وصيغ WebP/AVIF، وعدم وجود استعلامات N+1 واضحة.
**♿ الوصولية (البند 24):** تسميات `aria-label` للأيقونات، والتنقل بلوحة المفاتيح، وتباين ≥ 4.5:1، ومناطق لمس ≥ 44px.
**🌍 RTL واللغات (البند 30):** `dir="rtl"`، و Logical Properties، ولا نصوص مكتوبة داخل المكونات، وتنسيق التواريخ والأرقام بـ `Intl`.
**🔍 SEO (للويب):** عنوان ووصف لكل صفحة، و Open Graph، و `robots.txt` و `sitemap.xml`، وصفحة 404 مفيدة.
**📱 متطلبات المتاجر (للجوال):** أيقونات وشاشة البداية، ونصوص طلب الأذونات بالعربية، ورابط سياسة الخصوصية، وعدم رفع ملفات التوقيع (keystore) إلى Git.
**💾 النسخ الاحتياطي:** نسخ احتياطية لقاعدة البيانات مفعّلة في المنصة، وخطة استعادة مجرّبة مرة واحدة على الأقل.
**📈 المراقبة:** تتبّع الأخطاء في الإنتاج (خدمة مراقبة أو سجلات المنصة)، ورسائل خطأ ودّية للمستخدم بدل الأكواد التقنية.
**⚖️ القانوني:** صفحة سياسة الخصوصية وشروط الاستخدام، ووضوح جمع البيانات الشخصية.

## 4. التقرير
1. احفظ `docs/launch-report.md` مغلّفاً بـ `<div dir="rtl">` (مع سطر فارغ بعد الوسم وقبل إغلاقه): التاريخ، الحكم، جدول لكل مجموعة `| البند | الحالة | كيف تحققنا | الإصلاح المطلوب |`.
2. الحكم: 🟢 **جاهز للإطلاق** (لا ❌ ولا ⚠️ في الأمان) · 🟡 **جاهز بملاحظات** (⚠️ خارج الأمان فقط) · 🔴 **غير جاهز** (أي ❌، أو ⚠️ في الأمان).
3. الأخطاء الفعلية ← `bugs_log.md`. التحسينات غير العاجلة ← Backlog (القسم 12 في `project_map.md`) بمصدر `launch-check`.
4. وضع `production`: أوصِ بتشغيل `/consensus-gate` على الفرع كاملاً قبل النشر.
5. اعرض للمستخدم ملخصاً: الحكم، وأهم 3 إصلاحات مرتبة حسب البند 0، ثم اسأل بأداة AskUserQuestion (header: `الإطلاق`): `ابدأ بإصلاح الأهم`، `اعرض التقرير كاملاً`، `أطلق رغم الملاحظات` (يُخفى هذا الخيار إذا كان الحكم 🔴).
6. نفّذ `/document` بنوع `docs(launch)`، ثم "بروتوكول الاقتراحات".
