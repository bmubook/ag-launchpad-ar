# /document — التوثيق الإلزامي بعد كل تعديل

> **المرجع:** `master_rules.md` §2 (إلزامية التوثيق + ختم التوثيق) و §3 (الهوية النشطة)، والبند 8 في `rules_workflow.md`.

- نفّذ هذا الإجراء **بنفسك** بعد كل تعديل كودي ناجح يعبر الفحص، في الرد نفسه، دون انتظار طلب المستخدم.
- إذا انتهى الدور وقد عُدّلت ملفات كود دون تحديث `changelog.md`، يوقفك Hook الإيقاف (`stop-docs-check.mjs`) مرة واحدة بتذكير. عندها نفّذ هذا الإجراء فوراً ثم أنهِ الرد.
- المدخلات `$ARGUMENTS` (اختيارية):
  - قيمة خانة إجماع (تبدأ بـ 🔒 أو ⚡ أو 🎨، أو هي `مراجعة ذاتية`) كما يمرّرها `/consensus-gate` ← اكتبها كما هي في خانة الإجماع (الخطوة 5).
  - أي نص آخر ← اعتمده أساساً لصياغة الوصف في الخطوة 2.

| الحالة | ما تفعله |
|:---|:---|
| تعديل نجح في الفحص والاختبارات | نفّذ الخطوات 1-9 كاملة |
| تعديل فشل بعد استنفاد المحاولات (البند 8) | لا تسجّله في `changelog.md` كنجاح؛ نفّذ الخطوة 7 فقط (خطأ بحالة مفتوحة) ثم الخطوة 9 |
| لا توجد تعديلات غير موثّقة | اكتب `لا توجد تعديلات غير موثّقة.` وتوقف دون ختم |

## الخطوات

### 1. افحص التعديلات
1. شغّل عبر أداة Bash:
   ```bash
   git status --porcelain
   git diff --stat
   git diff --stat --cached
   ```
2. إذا فشلت الأوامر لأن المشروع غير مهيأ لـ Git، فاعتمد قائمة الملفات التي عدّلتها بنفسك في هذه المهمة.
3. استبعد ملفات السجلات التي يحدّثها هذا الإجراء (`changelog.md`، `bugs_log.md`، `decisions_log.md`، `project_map.md`) ما لم تكن هي موضوع التعديل.
4. لا تكرّر توثيق تعديل سُجّل في صف سابق من `changelog.md`.

### 2. حدّد نوع التغيير والنطاق (Conventional Commits)

| النوع | متى يُستخدم | أثره على الإصدار |
|:---:|:---|:---:|
| `feat` | ميزة جديدة | MINOR |
| `fix` | إصلاح خطأ | PATCH |
| `refactor` | إعادة هيكلة دون تغيير السلوك | PATCH |
| `security` | تحسين أمني أو سد ثغرة | PATCH |
| `docs` | تحديث التوثيق فقط | PATCH |
| `chore` | صيانة: إعدادات، اعتماديات، أدوات | PATCH |
| أي نوع مع `!` | تغيير جذري غير متوافق (Breaking Change) | MAJOR |

- **النطاق (scope):** اسم الوحدة بالإنجليزية بحروف صغيرة، مثل `auth` أو `db` أو `api` أو `ui` أو `rules` أو `deps`.
- **الوصف:** `type(scope): وصف عربي مختصر` — مثال: `feat(auth): إضافة تسجيل الدخول بـ Google`. التغيير الجذري: `feat(api)!: نقل جميع المسارات إلى /api/v2`.
- إذا جمع التعديل أكثر من نوع فاختر الأعلى أثراً (Breaking ← `feat` ← البقية) واذكر الباقي داخل الوصف.

### 3. احسب الإصدار التالي (Semantic Versioning)
1. اقرأ آخر صف في الجدول تحت `## جدول التغييرات` (الصفوف تُضاف في الأسفل، فآخر صف هو الأحدث). تجاهل أي صف يحتوي "لا توجد".
2. إذا لم يوجد أي صف حقيقي فالإصدار هو `v0.1.0`.
3. وإلا فطبّق:

| النوع | القاعدة | مثال انطلاقاً من `v1.4.2` |
|:---|:---|:---:|
| Breaking (`!`) | MAJOR + 1 وتصفير الباقي | `v2.0.0` |
| `feat` | MINOR + 1 وتصفير PATCH | `v1.5.0` |
| `fix` / `refactor` / `security` / `docs` / `chore` | PATCH + 1 | `v1.4.3` |

### 4. احصل على التاريخ والوقت المحليين
```bash
date "+%Y-%m-%d %H:%M"
```
إذا فشل الأمر فاستخدم:
```bash
node -e "const d=new Date(),p=n=>String(n).padStart(2,'0');console.log(d.getFullYear()+'-'+p(d.getMonth()+1)+'-'+p(d.getDate())+' '+p(d.getHours())+':'+p(d.getMinutes()))"
```

### 5. أضف صفاً واحداً إلى `changelog.md`
أضف صفاً واحداً في نهاية الجدول تحت `## جدول التغييرات` بالأعمدة الثمانية بالترتيب نفسه:

| العمود | القيمة |
|:---|:---|
| التاريخ والوقت | ناتج الخطوة 4 |
| الإصدار | ناتج الخطوة 3 |
| نوع التغيير | النوع وحده دون النطاق: `feat` أو `fix` أو غيرهما |
| الهوية النشطة | القبعة الفعلية أثناء التعديل (§3): `Senior Project Manager` أو `Backend & Security Engineer` أو `UI/UX Expert` |
| الملفات المتأثرة | مسارات نسبية مفصولة بفواصل؛ إذا زادت على 6 فاذكر أهم 5 ثم `(+N ملفات)` |
| نوع الإجراء ووصفه التقني المختصر | سطر Conventional Commits من الخطوة 2 |
| مرجع Git | الـ hash المختصر إذا دخل التعديل في commit (`git rev-parse --short HEAD`)، وإلا اسم الفرع (`git branch --show-current`)، و `local` إذا لم يكن Git مهيأً |
| نتيجة درجات الإجماع | انسخ نتيجة آخر تشغيل لـ `/consensus-gate` في هذه الجلسة كما طُبعت (مثل `🔒 9 · ⚡ 8 · 🎨 9`) بشرط أن يكون قد راجع هذا التعديل نفسه؛ `مراجعة ذاتية` إذا اكتفيت بمراجعة ذاتية؛ `-` إذا لم تُجرَ أي مراجعة |

- ضع الصف مباشرة بعد آخر صف دون سطر فارغ بينهما (السطر الفارغ يقطع الجدول).
- إذا كان الصف الوحيد في الجدول صفاً يحتوي "لا توجد" فاستبدله بصفك.
- لا تضع علامة `|` ولا سطراً جديداً داخل أي خلية.
- عدّل الجدول بأداة Edit فقط (البند 14)، وحافظ على غلاف `<div dir="rtl">` إن وُجد.
- مثال صف صحيح:
  `| 2026-09-29 14:05 | v0.2.0 | feat | Backend & Security Engineer | src/services/notes.ts, firestore.rules, tests/rules/notes.test.ts | feat(notes): إضافة إنشاء الملاحظات مع قواعد الأمان | feat/notes | 🔒 9 · ⚡ 8 · 🎨 9 |`
- تحقّق بعد الإضافة أن الصف الجديد يحتوي 9 علامات `|` بالضبط.

### 6. حدّث `project_map.md` إذا تغيّر شيء
- **جدول المراحل (Milestones):** حدّث `نسبة الإنجاز` تقديراً واقعياً (المهام المنجزة من مهام المرحلة) دون مبالغة، والحالة: `⬜ لم تبدأ` ← `🟡 قيد التنفيذ` ← `✅ مكتملة`.
- **المرحلة النشطة:** عند اكتمال مرحلة غيّر القيمة بعد التسمية فقط في السطر `> ▶ **المرحلة النشطة حالياً:** ` واترك التسمية كما هي حرفياً؛ تقرؤها Hooks وسطر الحالة.
- إذا أضاف التعديل جداول أو نقاط API أو مجلدات جديدة فحدّث أقسام DB Schema و API وهيكلة المجلدات.
- لا تغيّر اسم المشروع أو طبيعته أو اسم النداء أو وضع التشغيل إلا بطلب صريح من المستخدم.

### 7. سجّل الأخطاء في `bugs_log.md`
سجّل كل خطأ ظهر عند التشغيل أو الاختبار أثناء هذا التعديل (فشل اختبار، خطأ تشغيل، انحدار Regression):
1. **جدول الملخص** تحت `## ملخص الأخطاء النشطة`: أضف صفاً `| # | التاريخ | الأولوية | الملف المتسبب | وصف مختصر للمشكلة | الحالة |` برقم تسلسلي، والأولوية 🔴 أو 🟡 أو 🟢 حسب مفتاح الأولوية، والحالة `✅ محلول` أو `⏳ مفتوح`. استبدل صف "لا توجد" إن كان الوحيد.
2. إذا أصلح هذا التعديل خطأً مفتوحاً سابقاً فغيّر حالته إلى `✅ محلول` وأكمل حقل طريقة الإصلاح في تفاصيله.
3. **التفاصيل** تحت `## تفاصيل الأخطاء الكاملة`: أضف قسماً بعنوان `### #<الرقم> — <عنوان مختصر>` بعد القالب، واملأ جميع حقول القالب دون حذف أي حقل. رقم المحاولة `N/3` في `production` و `N/5` في `prototype`. الجذر التقني تحليل حقيقي للسبب (البند 22) لا وصف للعَرَض.
4. لا تحذف القالب الأصلي؛ فهو مرجع للتسجيلات القادمة.

### 8. سجّل القرارات في `decisions_log.md`
القرار الكبير هو ما يغيّر بنية المشروع أو تقنياته أو أمنه:

| يُسجَّل | لا يُسجَّل |
|:---|:---|
| اعتماد تقنية أو مكتبة أو خدمة جديدة (البند 19) | تسمية متغير أو دالة |
| نمط معماري (البند 27) أو ترقية معمارية (البند 29) | تعديل CSS أو نص |
| تصميم مخطط قاعدة البيانات أو استراتيجية المفاتيح (البند 28) | إعادة ترتيب كود دون أثر بنيوي |
| استبدال إعداد افتراضي بمعيار حديث (البند 28) أو قرار أمني (قواعد الأمان، المصادقة) | إصلاح خطأ عادي |

1. أضف صفاً `| # | التاريخ | العنوان | الحالة | الملخص |` تحت `## جدول القرارات` بالحالة `✅ مُعتمد` أو `🔄 قيد المراجعة`. استبدل صف "لا توجد" إن كان الوحيد.
2. أضف قسماً بعنوان `### ADR-<الرقم> — <العنوان>` تحت `## تفاصيل القرارات` بجميع حقول القالب، والمرجع رابط توثيق رسمي.
3. إذا ألغى القرار قراراً سابقاً فغيّر حالة القديم إلى `❌ مُلغى` وأضف في ملخصه: `استُبدل بالقرار #<الرقم>`.

### 9. اختم الرد بختم التوثيق
إذا كان `وضع التعلّم` = `مفعّل` في `project_map.md` فأضف قبل الختم كتلة `🎓 تعلّم:` من سطرين أو ثلاثة بلغة بسيطة: ماذا فعلنا، ولماذا، وماذا كان سيحدث لو لم نفعله.

اجعل ختم التوثيق آخر سطر نصي في ردك، بهذه الصيغة حرفياً، مع وضع ✅ أو ⬜ بصدق:

`📋 التوثيق: ✅ changelog | ✅ project_map | ⬜ bugs_log (لا أخطاء) | ⬜ decisions_log (لا قرارات جديدة)`

| الملف | عند التحديث | عند عدم الحاجة |
|:---|:---|:---|
| changelog | `✅ changelog` | `⬜ changelog (لا تعديل ناجح)` عند فشل التعديل أو إلغائه، و`⬜ changelog (قيد التنفيذ — يُوثَّق عند الاكتمال)` لعمل جارٍ لم يكتمل بعد (لا تكتب صفاً ناقصاً) |
| project_map | `✅ project_map` | `⬜ project_map (لا تغيير)` |
| bugs_log | `✅ bugs_log` | `⬜ bugs_log (لا أخطاء)` |
| decisions_log | `✅ decisions_log` | `⬜ decisions_log (لا قرارات جديدة)` |

- لا تضع ✅ لملف لم تعدّله فعلياً في هذا الإجراء.
- لا تغلّف الختم ولا الرد بوسم `<div dir="rtl">`؛ ردود المحادثة في Claude Code تُكتب Markdown عربياً نظيفاً.

### 10. الاقتراحات بعد المهمة المكتملة
إذا اكتملت المهمة فعلاً (ليست `قيد التنفيذ` ولا فاشلة) و`اقتراحات التطوير` = `مفعّلة` (أو غير محددة) في `project_map.md`، فنفّذ بعد الختم مباشرةً "بروتوكول الاقتراحات" من `.claude/skills/next/SKILL.md` (القسم `## بروتوكول الاقتراحات`).
